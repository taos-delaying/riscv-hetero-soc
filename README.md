# riscv-hetero-soc

基于 RISC-V 的可扩展异构计算与软硬件任务调度毕业设计。

更新日期：2026-11-19。本文作为项目长期维护的说明与对话交接入口，整合早期《本科毕业设计项目记忆》和当前工程进展。后续修改以新的明确决定为准。

## 课题背景与长期规划

毕业设计于 2026-10-29 调整为：从零自研两到三个 DSE 专用计算核，结合开源 RISC-V 核，探索运行时的软件调度与硬件调度。保留 DSE 这一项目术语；专用核可以是完成特定算子的 Verilog 模块，不要求每个核都具备完整 CPU 的取指、译码和指令集。

总体组织形式为独立 host、FFT、GEMV 和 Zircon RVV 工作核。FFT、GEMV 是自研计算核的方向，第三个自研核尚未确定；Zircon 为开源集成部分，与 host 是独立实例。当前 host 已选定 PicoRV32。

host 用裸机 C 程序组织和提交任务，计算引擎负责执行。计划在统一任务适配器后加入硬件调度器，管理任务与依赖，先实现顺序 FIFO，再研究就绪任务选择和乱序派发。任务控制接口倾向采用简单的 valid/ready 握手，不要求为此引入 AXI。

应用目标是传统主动音频降噪 ANC，保留用户最初“不带网络”的约束。规划使用 60 秒音频、无操作系统，数据和结果放在 SRAM，通过仿真导出文件试听。算法、采样率、精度和完整数据存储方案仍待确定；当前 64 KiB RAM 是小规模集成配置，不能据此认为已经解决整段音频的存储或实时处理问题。Verilator/VCS、FPGA 和现场演示属于原有验证规划，目前已开展的是 Vivado 行为仿真。

**当前 SoC 尚未接入 GEMV、Zircon RVV、任务调度队列或 ANC 应用。** 这些是后续方向。

## 当前已经实现

目前完成了从 C 程序到 FFT 硬件再回到共享存储器的基本执行链路：

```text
soc_top
├── cpu  : picorv32_new
├── fft  : pcpi_dispatch
│   └── fft32_dit2 及其子模块
└── sram : soc_sram_dp
```

- CPU 按 RV32I 使用，开启外部 PCPI 和周期计数器，默认不启用 M/C 扩展、IRQ 或 trace。`picorv32_new` 在保留必要功能和许可的基础上，清理上游调试、形式验证及无关包装代码，尽量减少功能改动。
- CPU 与 `pcpi_dispatch` 是平级模块，由 `soc_top` 连接。共享 RAM 为 16384 × 32 位，即 64 KiB；CPU 和 FFT 分别使用双口同步 RAM 的两个端口。
- 当前只按固定 32 点复数 Q1.15 FFT 使用，总缩放为 1/32。每个 32 位字的低 16 位是实部，高 16 位是虚部。
- 自定义指令通过 `rs1`、`rs2` 分别传入源、目的缓冲区的字节地址。控制器自行读取数据、计算并写回 RAM，完成后结束 PCPI 指令，不写 CPU 通用寄存器。软件当前采用输入输出同址的原地计算。
- 软件提供统一的 `fft32_q15()` 接口，通过 `FFT_IMPL=sw` 或 `FFT_IMPL=hw` 选择 NMSIS 标量软件实现或自定义指令封装。启动文件、链接脚本及 ELF、HEX、MAP 生成流程均已补齐。
- 系统测试台支持两版固件，检查完成标志和 FFT 输出，读取函数调用周期，并对硬件调用进行分阶段统计。

当前 FFT 指令是阻塞式的：CPU 等待结果写回后才继续执行。源码中保留的其他点数模块或译码信号，不代表已经开放相应的运行时接口。

## 讨论中的主要取舍

**复用开源 host，把自研工作集中在计算与调度上。** 用户已有独立实现 LoongArch 五级流水 CPU 的经历，本次仍选择具有 PCPI 接口的 PicoRV32，以减少重新设计指令交接、等待和返回机制的工作。CPU 与适配器分开，也便于以后接入其他计算核。

**通过共享 SRAM 传递样本，通过 PCPI 传递地址。** 相比 CPU 逐个传送 32 位样本，地址方式让控制器承担数据搬运，便于后续连接更多算子。但计算核仍需要明确的访存端口、时序和缓冲区约定，PCPI 本身不提供数据存储器访问能力。

**先固定 32 点，把完整链路跑通。** 已讨论运行时选择 N，但仅实例化多个完整 FFT 再选择输出会增加面积；真正复用硬件还涉及存储映射、级数、旋转因子和控制调度。因此暂不展开可变点数。这里也区分了“通过参数生成某种硬件”和“同一硬件运行时改变 N”。

**采用固定缩放，并保留精度问题作为后续研究。** 当前每级缩放累计为 1/N，硬件以截位处理，不做饱和裁剪；任意满幅复数输入仍可能溢出回绕。软件与硬件的运算、截断和饱和顺序不同，不能要求所有输入天然逐位一致。

**用统一函数接口选择实现，暂不修改编译器。** 同一应用调用 `fft32_q15()`，构建时链接对应实现；开启硬件版并不意味着编译器会自动识别任意 C 写法的 FFT。这样能够先建立可维护的软硬件对照，再考虑更复杂的编译支持。

**先采用阻塞式调用，再讨论异步任务调度。** 当前方案便于保证结果可用后函数返回。未来若希望 CPU 与计算核并行，需要另外设计任务保存、提交和完成反馈。早期“RS2 表达依赖”的设想尚未落实，当前 RS2 已用于输出地址；未来协议必须重新明确，不能直接套用旧字段含义。

**优化要区分时延、带宽、面积和切换活动。** 消除无用操作不一定缩短关键执行路径；增加计算并行度也不一定能突破存储带宽。后续应结合实际瓶颈选择优化方向，避免只比较蝶形数量或单次周期数。

## 用户已经验证的结果

用户已在服务器生成软件版、硬件版固件，并在本机 Vivado 行为仿真中分别得到 PASS。当前用例为 32 个 `0.5+j0`：按 1/32 缩放后，直流分量为实部 16384、虚部 0，其余频点为零。

最新加入调用前后计时的结果如下：

| 测量范围 | 软件版 | 硬件版 |
| --- | ---: | ---: |
| `fft_cycles`：FFT 函数调用区间 | 79731 | 104 |
| `program_cycles`：包含启动和输入准备的程序区间 | 81341 | 1714 |

在当前配置和用例下，调用区间加速比约 766.64 倍，整段程序约 47.46 倍。`fft_cycles` 包含调用、返回和计时开销；硬件版还包含 PCPI 交接、SRAM 读取和写回，未扣除空区间基线。软件基线运行在未启用 M 扩展的 RV32I 配置上，这不是所有软件 FFT 实现的通用性能结论。

硬件 104 周期已由测试台观察与软件计数器交叉核对：请求前 20、请求到首读 2、输入读取与采样 32、计算等待窗口 6、结果写回 32、写回到应答 2、应答到结束计数 10。计算等待窗口不是已测得的纯蝶形最短延迟。

当前结果只验证了这一输入用例，尚未形成完整的数值验证或当前 SoC 的面积、功耗、实现频率结论；测试台的 10 ns 时钟也不是实际 100 MHz 时序收敛的证明。早期未加入计时的程序周期属于另一测量版本，不与本表混用。

一个需要保留的调试经验：本机仿真曾在 `$readmemh` 加载 HEX 时出现未知字，改为本地数组中转仍失败，最终采用逐行解析后通过。确切根因未证明，不能直接归因于 CRLF 或某一 Vivado 缺陷。当前测试台负责加载镜像，DUT 的 `MEM_INIT_FILE` 保持为空，避免重复初始化。

## 当前问题与后续规划

2026-11-19 确认的时间条件：每周约 30 小时，距交付或答辩约四五个月。后续主线为 **可靠的 FFT＋第二个自研核＋任务调度对照实验＋完整应用**，优先补齐系统能力和实验依据。

以下按规划启动后的周次估算，包含学习、实现和联调；每周预留约 5～6 小时记录、阅读和整理材料。目标是第 16 周冻结功能、第 18 周达到可提交状态，第 19～20 周仅在实际截止日期允许时作为缓冲。

| 预计时间 | 阶段目标 | 阶段完成标志 |
| --- | --- | --- |
| 第 1～2 周 | 明确验收范围；补充 FFT 验证；建立 ANC 短片段软件参考；摸底 Zircon 与 FPGA 条件 | FFT 有多类输入参考；明确应用算子、规模、依赖及 GEMV 第一版规格 |
| 第 3～4 周 | 实现并独立验证 GEMV 第一版，先固定规模与精度 | 第二个自研核正确运行，有数值误差和周期记录 |
| 第 5～6 周 | 分离 PCPI 提交与核内执行控制，建立异步任务接口和共享 RAM 访问规则 | CPU 提交后可以继续执行；参数被锁存，结果写回后才报告完成，多核访存不冲突 |
| 第 7～8 周 | 实现带依赖检查的 FIFO 基线，再增加简单就绪任务选择 | 两种策略均正确，在相同计算核、存储条件和任务图下得到可解释的对照数据 |
| 第 9～11 周 | 按前期摸底结果接入 Zircon RVV，或完善核心系统 | 若接入，完成真实向量任务的提交、执行和完成反馈；范围调整与导师确认 |
| 第 12～14 周 | 将已验证的 ANC 算法映射到系统，处理分块输入输出和定点误差 | 应用结果与参考按约定误差范围一致，明确各算子映射及数据搬运开销 |
| 第 15～16 周 | 完成最终 FPGA 集成、时序与资源测量、系统性能实验 | 固定可复现版本，取得主要实验数据，冻结功能 |
| 第 17～18 周 | 完成论文、架构图、实验分析与答辩演示 | 达到可提交、可答辩状态 |
| 第 19～20 周 | 修复问题、补充实验与演练 | 作为缓冲，不承担新的核心功能 |

主要取舍与执行条件：

- **算法需求先行。** 前两周先验证 ANC 软件参考，第 4 周前确认 FFT/GEMV 与应用匹配；后期只做集成，不再重新选算法。当前 64 KiB RAM 不能默认容纳 60 秒音频，需提前明确分块加载和结果导出。若需要其他 FFT 点数，优先考虑固定配置。
- **先可靠，再扩展。** FFT 补充移位冲激、复数单频、随机、边界输入及连续调用；分别检查定点实现正确性与数学误差，不要求 NMSIS 和硬件天然逐位一致。GEMV 首版先做清楚的乘加结构，不同时追求多规模与高并行度。
- **调度和访存一起设计。** 区分任务接收、派发和结果完成，明确队列满、参数锁存与缓冲区生命周期。当前 FFT 依赖固定 SRAM 时序，多核共用端口需要明确仲裁或独占规则，不能只增加选择器。
- **用对照实验区分收益。** 保留纯软件、硬件阻塞调用、异步 FIFO、就绪任务选择四组方案，分别观察算子加速、执行重叠和调度策略的作用；同时记录无明显收益的串行或存储受限用例。
- **高风险集成提前摸底。** Zircon 三周预算以已有可运行基线、工具链和接口清楚为前提；若为必交项且条件不足，应提前重排计划。FPGA 前两周确认板卡与资源条件，第 4～6 周由用户尝试当前 SoC 的综合或最小上板，不等最终阶段才首次接触。
- **控制范围，保留收尾时间。** 暂缓运行时可变 N、第三个自研核、大规模存储带宽改造、复杂双缓冲和编译器自动识别 FFT。若实际仅剩四个月，提前与导师确认收缩条件项，不挤占验证和论文时间。上述阶段仍由用户运行编译、仿真和实现。

当前待处理事项：一次 FFT 仍统计到 36 次 SRAM 读取、32 次有效采样和 32 次写回；消除 4 次多余读取的方案尚未实施。可在多核访存改造前安排约半天到一天清理并验证。由于这些读取与已有阶段重叠，预计调用仍为 104 周期，不能作为节省 4 周期或已降低功耗的结论。缓冲区对齐和范围目前仍由软件保证，dispatcher 的地址合法性检查也需随接口整理明确。
